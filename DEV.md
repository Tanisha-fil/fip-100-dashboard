# DEV.md

## What this is

A fully static Filecoin FIP-100 metrics dashboard. Python scripts query BigQuery and emit JSON into `public/`. Astro reads those JSONs at build time and renders Chart.js charts. GitHub Actions regenerates everything every 6 hours and deploys to GitHub Pages.

## Commands

```bash
# Run all dataset scripts (requires ENCODED_GOOGLE_APPLICATION_CREDENTIALS)
make data

# Run a single dataset script
uv run --project datasets datasets/<name>.py

# Start local dev server (no data generation)
npm run dev

# Type-check Astro files
npx astro check

# Build the site
npm run build
```

After every change, run `npx astro check && npm run build` to verify.

To run dataset scripts locally, set the env var:
```bash
export ENCODED_GOOGLE_APPLICATION_CREDENTIALS=$(base64 -i /path/to/service-account.json)
```

## Architecture

```
datasets/*.py  →  BigQuery (lily-data.lily.*)  →  public/*.json  →  Astro build  →  dist/
```

- **`datasets/`**: Python scripts, each queries one or more BigQuery tables and writes a single JSON to `public/`. Managed by `uv` (Python ≥3.14, deps: `google-cloud-bigquery`, `polars`).
- **`public/*.json`**: gitignored — regenerated by CI on every deploy.
- **`src/pages/index.astro`**: imports all JSONs at build time, passes data as props to chart components.
- **`src/components/LineChart.astro`**: single-series chart (one `y` column).
- **`src/components/MultiLineChart.astro`**: multi-series chart (`ys` array of columns, `labels` array).

Both chart components serialize data into a `data-*` attribute on a `<canvas>`, then hydrate with Chart.js in an inline `<script>`. They both hardcode the nv25 (2025-04-14) and nv26/+90d (2025-07-13) vertical annotation lines.

## Key BigQuery tables (lily-data.lily.*)

| Table | Used for |
|---|---|
| `power_actor_claims` | Raw/QAP power per miner (change-driven, requires fill-forward) |
| `derived_gas_outputs` | Gas fees per message |
| `parsed_messages` | Message method names, sector batch sizes, DDO detection |
| `chain_economics` | Circulating supply, burnt FIL |
| `miner_sector_events` | SECTOR_EXPIRED / SECTOR_EXTENDED events; also used as chain-state fallback for sector counts |
| `miner_sector_infos_v7` | Per-sector declared lifetime, daily_fee |
| `block_headers` | parent_base_fee per block |
| `chain_rewards` | Block rewards |

**Epoch → timestamp**: `timestamp_seconds((height * 30) + 1598306400)`. Height cutoff for the analysis window: `height > 4000000`.

**nv25 epoch**: 4878840. **Grace period end epoch**: 5138040.

## Parsed message param fields (corrected per Starboard)

When parsing `lily-data.lily.parsed_messages.params`:

| Method | Correct field for sector count | Notes |
|---|---|---|
| `PreCommitSectorBatch2` | `$.Sectors` (array length) | Reliable |
| `ProveCommitSectors3` | `$.SectorActivations` (array length) | **Not** SectorNumbers/SectorProofs/Sectors — those are the wrong fields |
| `ProveReplicaUpdates3` | `$.SectorUpdates` (array length) | |
| `ProveCommitAggregate` | `$.SectorNumbers` (array length) | Do **not** use `$.AggregateSize` or `$.AggregateSectorCount` — unreliable |

**DDO detection** (ProveCommitSectors3 / ProveReplicaUpdates3):
- A sector is DDO if `SectorActivations[i].Pieces[j].Notify` is null or does not contain `{"Address": "f05"}`
- A sector is non-DDO (traditional StorageMarket path) if any piece has `Notify[0].Address = "f05"`
- CC sectors (`Pieces = null`) are DDO by convention
- Source methodology: Starboard notebook

**Data source philosophy** (per Starboard):
> Use chain state (miner_sector_events SECTOR_ADDED) as primary source for sector counts where possible. Use params as fallback. Params are fragile — param structures have changed across FIPs and methods have changed several times historically. Exception: DDO detection requires params because the Notify field is only available there.

## Data pipeline patterns

- **Fill-forward** (`power_actor_claims`): the table is change-driven — a miner only has a row when their power changes. To get smooth daily totals, fill each miner's last known value forward to missing days, then diff day-over-day. Seed pre-window miner state from `height <= 4000000` via a virtual anchor row to avoid day-1 artifacts.
- **7-day rolling mean**: applied in Python (polars) before writing JSON for metrics with small daily denominators or noisy single-day events (currently: `power_added.py`, `renewal_rate.py`). Update the chart subtitle to say "(7-day avg)" when applying.
- **Units**: raw power in bytes → divide by `pow(1024, 5)` for PiB. Gas in attoFIL → divide by `1e9` for nanoFIL or `1e18` for FIL.

## Chart component rules

- Use `LineChart` for one series, `MultiLineChart` for two or more.
- Chart.js color values in the component `<script>` must be **concrete hex/rgba strings** — no CSS custom properties (`var(...)`) inside JS chart config. CSS variables can be used in `<style>` and read with `getComputedStyle` where needed (see `LineChart.astro`).
- The shared color palette in `MultiLineChart.astro`: `["#0f172a", "#2563eb", "#16a34a", "#d82124", "#9333ea", "#ea580c"]`.
- Both components filter out null/non-finite points before rendering.

## Adding a new chart

1. Write `datasets/<name>.py` — query BigQuery, write `public/<name>.json` with a `date` column (formatted `%Y-%m-%d`) and metric columns.
2. Import the JSON in `src/pages/index.astro`.
3. Add a `<LineChart>` or `<MultiLineChart>` in the appropriate category section.
4. Run `make data` (or `uv run --project datasets datasets/<name>.py`) then `npm run build`.
